## 0. 一句话

把"**一整轮压成一个气泡、工具行统一堆在正文上方**"改成"**按时间顺序依次渲染**"（dashboard 的读法）：
正文片段 / 工具行 / 正文片段 交错出现，工具行变成**常驻小字行**（灰字 + 缩进、不折叠）。

## 1. 为什么（用户 2026-09-15 点出的实际问题）

现在的渲染顺序是**被 `normalize()` 揉过**的：

- `normalize()` 规则 5「连续 assistant 合并成一段」→ 一整轮的多段正文被拼成一个气泡；
- `attachPending()` 把本轮所有工具**统一挂到**那条合并后的回复**上面**。

后果：**"哪段话之后调了什么"这个顺序信息丢了**。直接咬到的地方就是刚做完的补充信息（steer）——
用户插进来的那句话，**放在上面不对、放在下面也不对**，因为在模型真实的时间里它落在某个中间位置。
服务端历史本身是分条的（`assistant(正文+tool_calls)` → `tool(结果)` → `assistant(正文+tool_calls)`），
所以改造本质是：**把那条合并规则反过来，让每段落在它真实的时序位置**。

## 2. 口径（用户 2026-09-15 已拍板，不再改）

| 项 | 定论 |
| --- | --- |
| 工具行形态 | **常驻小字行**（灰字 + 缩进，**不折叠**，dashboard 式）；不要折叠开关 |
| 先后 | 先做第 12 条（相位分派），**本条单独立项**（避免两条一起上、真机验收分不清是谁的问题） |
| 交错粒度 | 按**时间**：正文段 / 工具行段 交替；用户消息与压缩摘要保持独立块 |
| 轮内/轮间 | 轮内紧凑（同一轮的各段挨得近），轮间留白（仍能一眼看出一问一答） |

## 3. 设计

### 3.1 数据模型（最小改动，不引入状态机）

`UiMessage` 加一个字段：`kind?: 'text' | 'tools'`（缺省 `'text'`，老路径不用改）。

一轮 = `user 块` + 若干段，段只有两种：`text`（markdown 正文）、`tools`（那一时刻的工具行）。
**轮级标记**（`stats` / `interrupted` / `error` / 流式光标）挂在**本轮的最后一个段**上 ——
渲染上它天然就是"这一轮的页脚"，且不用为它单开一层结构。

为什么不引入 `UiTurn { segments: [] }` 包一层：那要动渲染、滚动锚定、分页与所有既有断言，
收益只是"更好看的分组"。用扁平列表 + 纯函数分组（§3.2）能得到同样的 DOM，风险小得多
（用户原则：简单稳定 > 功能齐全）。

### 3.2 渲染

- `lib/turns.ts` 新增纯函数 `groupIntoTurns(msgs)`：把扁平列表按"user 块后面跟的连续段"分组成轮，
  供 `ChatWindow` 用 `v-for` 渲染 `轮`（轮内 `space-y-2`，轮间 `mt-6`）。
  纯函数 ⇒ 可单测、可被真浏览器脚本复用。
- `MessageItem` 的 `kind === 'tools'` 分支：渲染常驻小字行（`●/✓/✗ 名称 "参数预览" (耗时)`），
  灰字 + 缩进 + 左侧细线；删掉 `tools-toggle` 按钮与 `toolsOpen` 状态（不折叠）。
- 轮级页脚（统计行 /「已中断」/ 错误）改为**两种 kind 都渲染**（挂在最后一个段上，天然是页脚）。

### 3.3 实时链路（边跑边交错）

> **实现时改掉的一处（写在这里免得下次又踩）**：原先计划"`send()` 立刻插一个空正文段当占位"。
> 实现时发现那样会造出**空正文段这种假东西** —— 只要这一轮开口先调工具（很常见），
> 界面上就是"空气泡 + 工具行 + 正文"。改成**按需创建**：第一段是工具行就是工具行、第一段是正文就是正文；
> 思考阶段的进展由状态条（`RunStatus`）如实说。单测里两条断言专门锁这个（"没有空正文段"）。


- `send()`：推 `user` 块 + 一个空的 `text` 段（`streaming: true`，记进 `ctx.segs`）。
- `message.delta`：写进**当前 text 段**；若当前段已因工具而"封口"，则**新开一个 text 段**（交错的关键一步）。
- `tool.started`：先把当前 text 段封口（`streaming=false`），再**新开一个 tools 段**放这一步；
  `tool.completed/failed` 就地更新那一步的成败与耗时（步骤对象与 `store.run.timeline` 同源，两个视图同步）。
- 轮末（`run.completed` / cancelled / error / 网络收尾）：`reconcileTurn()` 改成
  **用服务端 transcript 重建本轮的段**（`normalize(turnSlice(raw, sentText))`，替换流式期拼出来的段），
  再把 `stats/interrupted/error` 挂到最后一个段。拿不到 transcript（断网）→ 保留流式段，只把 `streaming` 关掉。

### 3.4 分页与去重（既有机制要保持有效）

`prependEarlier()` 的边界合并**只允许同 kind**：`text`+`text` 合并正文、`tools`+`tools` 合并步骤，
`text`+`tools` 一律不合并（直接首尾相接）。`loadEarlier()` 按 `srcId` 去重的逻辑不变。

## 5. 已知取舍与风险

- **"补充（steer）落在哪"仍不完美**：补话注入到的是**最近一条工具结果末尾**，而它显示成独立用户块
  （不参与段序）—— 这是 steer 接口本身的语义限制，本条只保证"正文与工具的先后是对的"。
  要把补话也插进时间流，得改 Hermes 侧（HTTP 未暴露 `redirect`），不在本条范围。
- 长轮次的 DOM 节点会变多（原来一个气泡装十几段，现在十几段 + 几十个工具行）——
  这正是当初做折叠的原因；用户已明确选择"常驻小字行"，接受。
- 滚动锚定的旧判据（v2.6，坑 50/51）是在"合并成一条"的前提下调出来的，**必须重跑**（§4.5）。
