# 模块 02 · 状态层（`src/stores/chat.ts`）

> **一句话**：全项目**唯一**的 store，也是**唯一的复杂度中心**（1899 行 / 全仓 10.7k 行）。
> 它同时是：会话缓存、段归约器、发送状态机、断线恢复协调器、统计口径实现、上游缺陷兜底。
> 读懂它 = 读懂这个项目。

## 1. 为什么是一个文件（以及它的代价）

- **理由**：只有一个会话视图，`reactive()` 足够 ⇒ 不引 Pinia；而发送状态机、轮末对账、
  断线恢复这三件事**天然共享同一批状态**（相位、timeline、ctx、abortCtl），拆开反而要靠回调串起来。
- **代价**（评审重点，详见 `文档/04` B1/缺陷 A1）：**模块级可变状态有 7 处**
  （`abortCtl`、`loadedIds`、`transport`、`stopRequested`、`watching`、`watchAttempt`、`bootErrorTransient`），
  它们跨越了会话与页面边界。缺陷 A1（跨会话 run 状态串台，**2026-09-18 已修**）就是这类泄漏的一个实例。

## 3. store 的形状

```ts
store = {
  healthOk / healthVersion,          // 连接状态（顶栏与 Settings）
  sessions / sessionsLoading,        // 会话列表（已过滤 hidden/archived）
  currentId / messages / messagesLoading,
  rawCount / hasMoreHistory / historyLoading,   // 分页游标（offset 锚在"最新"）
  context: { model, limit, turnInput, stale, at },   // 输入框上方那一行的三个数字（三处来源）
  streaming / bootError,
  run: {
    phase: 'idle'|'thinking'|'tool'|'approval'|'writing'|'background'|'done'|'aborted'|'error',
    startedAt / endedAt,                 // performance.now() 基线（render 时算耗时）
    currentTool / toolPreview,           // 状态条用（工具名**不**进状态词）
    timeline: ToolStep[],                // 本轮工具调用（成败/耗时）
    errorMessage / blocked,              // 红字 / 安全闸门原文
    runId,                               // 中断与审批回话要它
    approval: ApprovalState | null,
    recovered,                           // 本轮内容是回读补齐的（界面要如实标注）
    syncing,                             // 正在跟服务端对齐（"正在同步…"）
  },
}
```

**两个不可交换的语义**（评审时最容易被误读）：

- `run.phase === 'background'` 表示"服务端那一轮还在跑，本地看不到" ⇒ 🟡 忙碌，**绝不报红**；
  它同时是 `send()` 的守卫之一（不能开第二轮）。
- `run.runId` 是"服务端到底有没有收到这一轮"的**唯一凭据** ⇒ 决定「重试」按钮是否出现
  （`null` = 没收到 ⇒ 重发安全）。

## 4. 段归约（②）：为什么"合并"和"交错"必须同时存在

`normalize(raw)` 的规则（v2.11 定稿，三条容易漏的见 `文档/02` §6）：

1. 丢掉非 `user/assistant/tool`；`content` 为数组时取 text 片段拼接；
2. **相邻正文仍然合并**（否则一轮碎成十几块、段间 24px 缝、复制出一堆空行）；
3. **工具段把正文切开**：段序 = `text → tools → text → …`（正文在前、工具在后，模型先说话后调工具）；
4. `role=tool` 结果行**不进段**，只按 `tool_call_id` 回填成败/耗时；
5. **当前工具段为空时新开一段**（孤儿结果行 —— 宁可多一行，也不丢"调过这个工具"）；
6. 压缩摘要消息单独标记（折叠显示、不参与任何合并）。

`prependEarlier(older, current)`（翻页拼接）**只在同 `kind` 之间合并**：`text+text`、`tools+tools` 合；
`text+tools` 一律首尾相接（合并就把顺序信息抹掉了，正是 v2.11 要修的东西）。

段 `key` 的取值：历史段用来源消息 id 派生（`h_${id}` / `h_tools_${id}`，**确定性**，分页拼接不会撞 key）；
实时段用 `tempKey()`（时间 + 随机）。轮末对账靠 key 集合做**整批替换**。

## 5. 分页与去重（①）

- 分页语义（实测）：`order` 只有 `oldest|latest`；`latest + offset=N` = **从最新往回数第 N 条**；
  页内按时间正序；接口不返回总数 ⇒ "还有没有更早"只能靠 `returned === limit` 判断；`limit` 上限 500，
  项目用 `HISTORY_PAGE = 100`。
- **必须单独维护 `loadedIds`**（模块级 `Set`）：连续 assistant 合并后，界面消息只保留该组最后一条的 id，
  中间 id 从界面上消失 ⇒ 拿 `srcId` 去重会漏（自测复现过同一段被加载两次）。
- 发过新消息后窗口整体位移与已加载内容重叠 ⇒ 靠 id 去重（`fresh = res.data.filter(m => !loadedIds.has(m.id))`）。
- 两种"到底了"：不满一页，或这一页**全是重复**（窗口已位移到没有新内容）。

## 6. 发送状态机（③）：一轮的五个阶段

```
send()  →  [守卫] → [懒建会话] → [读基线 counters] → [乐观插入用户气泡] → [resetRun + AbortController]
runTurn() → POST /v1/runs → writeActiveRun() → GET .../events → applyEvent 边收边画
finally → [封口段] → [查终态补判] → [reconcileTurn 对账] → [相位判定] → [统计] → [上下文缓存] → [刷新侧栏]
```

细节与失败矩阵见 `文档/02` §2–§9。这里只强调三个"设计上刻意如此"的点：

1. **不预建空正文段**：按需创建，避免"空气泡 + 工具行 + 正文"（曾因此改过一次实现）。
2. **工具段的成败/耗时是"两份数据按顺序拷贝"**（`syncToolsToMsg`），因为要"边跑边看" ——
   等轮末才出现的话，十几分钟的长任务期间界面只剩一行"正在使用 xx…"。
3. **每轮统计只给真正跑完的轮次**：被取消 / 被网关重启打断的轮次计数是半截的，算出来会误导。

## 7. 断线恢复（⑤）：三件小事，没有状态机

```
① 提交成功立刻 writeActiveRun({sessionId, runId, sentText, startedAt})   → hcl.activeRun（6h TTL）
② 回前台（visibilitychange/focus/pageshow/online）→ resumeSync()
     ├─ 无记录 / 当前打开的不是那条会话 → 什么都不做（v2.12：**不再自动切会话**）
     ├─ 本页还在流式 → getRun()：已终态就 abortCtl.abort()（让收尾逻辑跑起来）；否则 watchRun()
     └─ 否则 → applyRunStatus()：非终态 ⇒ 相位转 background + watchRun()；终态 ⇒ recoverTurn() 收尾
③ 轮询：backoff 1s→2s→…→30s 封顶；页面不可见时不轮询（回到前台立刻接手）
```

`applyRunStatus()` 的分支要点：`completed` → 对账、必要时用 `st.output` 兜底、**清掉传输层假报错**；
`failed` → 红字；`cancelled` → aborted；**`interrupted` 必须算终态**（漏了会"卡死 + 轮询永不停止"）；
`404`（run 已清理）→ 能对账就当完成，否则相位归 idle 并**清记录**。

## 8. 口径与缓存（⑥）

- `counters(sid)`：读会话累计（`input_tokens` / `cache_read_tokens` / `output_tokens` / `tool_call_count`），
  顺手把 `model` 带回 `store.context.model`（不用额外请求）。
- `buildStats({ms, usage, before, after})`：`uncachedInput = after.input - before.input`、
  `cacheRead = after.cache - before.cache`、`cacheRate = cacheRead / (uncached + cacheRead)`；
  输入优先用 `usage.input_tokens`（有就信它），否则退回差值。三者自洽（实测 706 + 26624 = 27330 ✓）。
- `rememberContextUse()`：记 `usage.input_tokens`（= **本轮输入合计**）到 store + `hcl.ctx.<sid>`。
  ⚠️ **它不是"当前上下文占用"**，所以界面**不显示百分比**（拿它除窗口曾显示假的 100%）。
- `loadModelInfo()`：`/api/model-info` → `effective_context_length`（经 nginx 转 dashboard 后端）；
  拿不到保持 `null`，界面少显示一段，**不编数字**。
- `setBootError()` / `clearTransientBootError()`：横幅分"网络抖动类"（下次成功即清）与
  "服务端明确拒绝类"（不清，否则等于把真问题藏起来）。

## 9. 上游缺陷兜底

`removeSession()` 删完后 `sweepGhost(id, 2000)` 复查一次：还读得到（迟到的异步 token 写入 upsert 重建了会话行）
就再删一次，顺手清掉列表里的同一具空壳；失败一律静默（这不是用户请求的操作）。根治要靠宿主机应用
`apply_ghost_fix.py`（需 root）。

## 10. 改这个文件的纪律

1. **`openSession()` / `goHome()` / `removeSession()` 的清理动作必须一致**（少一处"看起来一样但漏了一项"
   就是下一次 bug）—— 现在三处**统一走 `clearTurnState()`**：清掉 `runId`/计时/`timeline`/审批/错误
   + `stopWatching()`，但**刻意不清** `hcl.activeRun` 记录（回到那条会话还要靠它接上）。
   配合 `applyRunStatus()` 首行的**会话守卫**（不是当前会话就只停轮询、不动状态），
   把"run 状态只属于它所在的会话"这条不变式钉死；回归用例见 `src/stores/resume.spec.ts`
   的「★ 跨会话」一组（5 条，其中 4 条在旧实现上必红）。
2. **相位是字符串联合**：加成员时先 grep `isTerminalStatus|phase ===`，再改所有比较点；
   `lib/turnStatus.ts` 有编译期绊线，其余的没有。
3. **单测里 store 是模块级单例**：断言"启动态/空态"的用例必须在 `beforeEach` 里显式清
   `currentId/messages/sessions/run`，否则 RED 阶段会**假通过**。
4. 大规模改动先落计划书（`docs/plans/`），并**把被实况推翻的设计写进计划书**（例：原计划
   "send() 先插空占位段"，实测会产生空气泡 ⇒ 改成按需创建）。
