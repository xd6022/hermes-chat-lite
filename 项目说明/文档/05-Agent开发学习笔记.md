# 05 · Agent 开发学习笔记（读这个项目能拿到什么）

> 这一篇把"具体实现"抽成**可迁移到任何 agent 客户端的认知**。每条都附本项目里的对应位置，
> 方便你回到代码里看它是怎么被逼出来的。
> 结论先给：**接一个长跑型 agent，难点从来不在"把字流式显示出来"，而在下面 12 件事。**

## 1. 提交与订阅必须分离，任务执行不能依赖客户端连接

`POST /v1/runs` 返回 202 + `run_id` 就算"接单了"，run 由服务端自己跑完并落库 ——
**无人订阅也照跑**（实测：无人订阅的 run 24s 后 completed、正文已落库）。
一旦接受这一点，客户端的架构会立刻简化：不需要保活、不需要心跳、不需要连接管理器。

> 反面教材：把"任务"实现成"一个长连接的 POST 流"。那种设计下，用户一刷新页面任务就没了，
> 你会被迫去写"断线重连 + 幂等恢复"，而这两件事本质上都在补同一个缺陷。
> 对应位置：`chat.ts:1180-1196` 的架构前提注释；`api/runs.ts` 文件头第 1 条。

## 2. 事件流是**提示**，不是**真相**

SSE 里的 `delta` 拼接出来的文本**不可靠**：实测带前导换行杂质、断线会丢字。
所以本项目在轮末必做一次 `reconcileTurn()`，用服务端落库的 transcript **整批替换**流式期拼出来的内容。

> 可迁移做法：把事件流当"低延迟的、可能丢的、有噪声的预览通道"；把"落库/状态查询"当权威。
> 两者用**同一个归一化函数**（`normalize()`）消费，实时与历史才不会慢慢长歪。
> 对应位置：`chat.ts:1140-1159`。

## 3. "界面不再变化" ≠ "任务已完成"：完成态必须显式判定

agent 的运行状态有好几种终态，而且**终止 ≠ 完成**：
`completed`（真完成）、`cancelled`（用户停的）、`failed`、`interrupted`（网关在这轮跑完前重启）。
早期实现把 `run.cancelled` 当完成 ⇒ 用户主动中断的那一轮显示成"完成"（真链路 e2e 抓到的真 bug）。

> 可迁移做法：显式列一张**终态表**，并区分"终止事件"与"完成事件"；
> 再加一条编译期绊线（把穷尽性检查写进类型系统），逼着后来者为新终态做决定。
> 对应位置：`lib/turnStatus.ts:116-124`、`isTerminalStatus()`、`chat.ts` 收尾的相位判定。

## 4. 断线不等于取消（这一条最容易被写错）

长任务的连接会因为切后台、锁屏、换网被系统掐掉。如果客户端把"连接断"当成"任务结束"，
就会出现两种灾难：① 界面误报"回复中断"，让人以为几十分钟的活白费；② 用户想停下时，
代码只是断了连接，服务端还在跑（旧通道就是这样）。

> 可迁移做法：**任务取消必须是一个显式的服务端调用**（`POST /v1/runs/{id}/stop`），
> 断流只影响"你能不能实时看到"。界面上还要把这两种状态分开显示：
> `background`（服务端还在跑，🟡）与 `aborted`（确实结束了，🟠）。
> 对应位置：`stop()`、`RunPhase` 的 `background` 注释、`turnStatus` 的判据表。

## 5. 恢复的最小充分集：一条页面之外的记录 + 一次状态查询 + 一次回读

页面被回收后，客户端会**彻底失忆**。解决办法不是"更强的连接"，而是三件很小的事：

| 要记得的东西 | 存哪 | 为什么不是别的 |
| --- | --- | --- |
| `{sessionId, runId, sentText, startedAt}` | `localStorage` | `sessionStorage` 扛得住刷新、**扛不住标签页被系统回收重建**（真机验证过） |
| 任务当前状态 | 服务端 `GET /v1/runs/{id}` | 客户端推不出来，也不该推 |
| 已经产出的内容 | `GET /api/sessions/{id}/messages` | 落库的才是权威 |

> 可迁移做法：拿到"任务 id"之后就把它**写进页面之外**；恢复触发只挂在"回到前台"这一个事件上
> （`visibilitychange`/`focus`/`pageshow`/`online`），退避轮询（1s→30s 封顶）且**页面不可见时不轮询**。
> **永远不要**用 `setInterval` 保活 —— 后台定时器会被 throttle，既不可靠又费电。
> 对应位置：`ACTIVE_RUN_*`、`resumeSync()`、`watchRun()`、`lib/page-lifecycle.ts`。

## 6. Human-in-the-loop：审批是一个**状态**，不是一次回调

有工具执行能力的 agent 一定会遇到"这步有风险，要不要放行"。本项目拿到的上游语义是：
在 `POST /v1/runs` 这条通道上，服务端会发 `approval.request` 并**停住等人回话**
（`once` / `session` / `always` / `deny`）；而另一条通道上同样的操作会**当场 fail-closed 拒绝**。

> 可迁移做法：① 审批必须能在**界面里**完成，且要显示"被拦下的原文"；
> ② 选项由服务端给（别写死）；③ 审批期间这一轮是"卡住"的，状态词要说清楚"不点就不会继续"；
> ④ 超时/拒绝 与 硬规则拦截 是两回事，文案要分开（前者可重试，后者任何客户端都放行不了）。
> ⚠️ 本项目已知缺口：审批卡片只活在事件流里，流一断卡片就丢（见 `文档/04` B5）——
> 这正是"审批状态应该尽量做成可查询的服务端状态"的论据。
> 对应位置：`applyEvent` 的 `approval.request/responded`、`RunStatus.vue` 审批卡、`lib/security.ts`。

## 7. Steering（轮中插话）的语义极窄，别想当然

"打断 + 把这句话并进同一轮"是 agent 内部的 redirect 能力，HTTP 层通常**只暴露 steer**：
文本被挂到**最近一条工具结果**末尾，模型下一次迭代才看到。由此推出三个必须知道的边界：
① 本轮没有工具调用 → 文本可能拖到轮末才回传（`pending_steer`）；
② run 刚好收尾 → 409，只能静默降级；
③ 它**不是一条独立消息**，所以刷新后不会再以"你的消息"出现。

> 反面做法：用"再提交一条消息"来模拟插话 —— 那会**并发第二条 run**（实测两条都 running、
> 历史落库顺序交叉）。**同一会话同一时刻只允许一条 run**，这是所有客户端都该守的不变式。
> 对应位置：`steer()` 的注释（含实测证据）、`canSteer()`。

## 8. Token / 成本观测：先分清"这一轮累加"和"当前占用"

agent 一轮会调用模型很多次。上游给的 `usage.input_tokens` / `session_prompt_tokens` 往往是
**该轮内每次调用 prompt 的累加**，不是"我现在占了多少上下文"。拿它去除窗口会得到荒唐的假水位
（实测：一轮 30 次调用累出 2.6m ÷ 1m ⇒ 界面显示 100%，而单次最大 prompt 只有 125k）。

> 可迁移做法：① 只显示有真实来源的量，**绝不编数字**（宁可少显示一段）；
> ② 想要"上下文占用"就必须让服务端在 HTTP 层暴露它（本项目拿不到，所以干脆不显示百分比）；
> ③ 缓存命中率、输出 token、墙钟耗时都是从"会话累计做差"得来的 —— 要清楚它**刷新即失**。
> 对应位置：`components/ContextGauge.vue` 文件头、`chat.ts:1847-1864`、`buildStats()`。

## 9. 上下文压缩是 agent 的**内部机制**，客户端要能识别并优雅处理

长会话会被服务端压缩，压缩产物以一条 `assistant` 消息的形式**落进历史**。如果原样渲染，
用户会在对话流里看到一大坨"[CONTEXT COMPACTION …]"。

> 可迁移做法：把压缩消息识别出来（**照抄上游的判据，别自创正则** —— 真实那条并不以标记开头，
> 标记出现在 100 字符之后）、折叠显示、并且让它**不参与任何消息合并**。
> 对应位置：`lib/messages.ts:23-30`。

## 10. 工具调用的可观测性 = 一个"时间线"，而不是一行状态

用户真正想知道的是：**哪段话之后、调了什么、花了多久、成功没有**。这就要求渲染模型支持
"一段回复 → 一批工具 → 下一段回复"的**交错结构**（本项目叫"段模型"），而不是"一轮一个气泡"。

> 可迁移做法：① 数据结构上把 `text` 段与 `tools` 段分开；② 实时事件与历史落库**走同一套归一化**；
> ③ 耗时用**本地时钟**（`performance.now()`）算，不用事件里的 `ts`（时钟/网络抖动会让它跳）；
> ④ 运行中的工具**不显示耗时**（只有跑完才有意义）。
> 对应位置：`UiMessage.kind`、`normalize()`、`openTextSeg/sealTextSeg/toolsSegFor`、`MessageItem.vue`。

## 11. 把上游当成**会变的契约**：收敛比较点，加哨兵

上游加一个新终态，客户端可能要在**四个地方**同时改（状态查询、收尾分支、统计判据、状态显示），
漏一个的表现不是"显示得差一点"，而是**界面永久卡在忙碌中 + 轮询永不停止**（真发生过）。

> 可迁移做法：① 终态/事件名/字段名/关键文案收成**单一常量模块** + 一个 contract 测试；
> ② 用类型系统的穷尽性检查把"新状态"变成**编译错误**而不是线上故障；
> ③ 记住 `JSON.stringify` 会丢 `undefined` 字段 ⇒ 上游字段改名时症状可能是"字段凭空少了一个"
>   （实测：工具名从 `tool_name` 变 `tool`，症状是工具名全空）。
> 对应位置：`lib/turnStatus.ts:116-124`、`api/runs.ts` 的归一化、`api/types.ts` 的白名单注释。

## 12. 可验证性要设计进去：可观测、可归因、可复现

- **可观测**：每个"状态显示"都要能回答"这个数字从哪来"（本项目把三份数据来源写进组件头注释）。
- **可归因**：构建时注入版本标识 + 判版本用**指纹**（入口 bundle 哈希 + 该版本独有文案 `grep -c`），
  这样"线上是哪一版"不用猜；`A/B 对照`（同一探针跑两次产物）用来回答"这是我这次引入的回归吗"。
- **可复现**：发现服务端缺陷时先写**复现脚本** + 直查原始行 + 按时刻捞日志，再回头读码（比盯着代码猜快得多）。
- **把静默的错变成响亮的错**：做不到"不犯错"时，让错误**大声**（构建期自检、静态资源真 404、
  healthcheck 打需要鉴权的端点）。
- 对应位置：`vite.config.ts` 的 `__BUILD_ID__`、`nginx.conf` 的缓存与 404 加固、
  `Dockerfile:27-31`、`docker-compose.yml:16-24`。

---

## 拿走这 5 句，接任何 agent 都用得上

1. **任务在服务端，界面只是投影** —— 断线不失忆、重连不重跑，靠"记录 + 查询 + 回读"三件小事。
2. **事件流是提示，落库是权威** —— 两者用同一个归一化消费者，别让两条渲染路径各自演化。
3. **完成态要显式判定，终止 ≠ 完成** —— 终态表写进类型系统，别散在字符串比较里。
4. **HITL 与 Steering 都是窄语义** —— 审批要能查、要不丢；插话只能 steer，别用"再发一条"模拟。
5. **观测与成本先分清口径** —— 拿不准来源的数字宁可不显示；观测能力不到位时，加功能只是加故障面。
