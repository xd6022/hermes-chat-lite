## 1. 键盘 → 输入框（组件层）

```ts
// components/InputBox.vue
onKeydown(e)  ── Enter 且 !shiftKey 且 非输入法合成期(composing/isComposing) ──▶ submit()
submit():  if (!text.trim()) return
           if (mode === 'stop') return         // 正文输出期 Enter 静默不提交（防误触打断输出）
           text.value = ''                     // 先清空输入框
           mode === 'steer' ? steer(v) : send(v)
mode = canSteer() ? 'steer' : busy ? 'stop' : 'send'     // :144
busy = store.streaming || store.run.phase === 'background'  // :136
```

| 相位 | 按钮 | 点它 / Enter |
| --- | --- | --- |
| 思考 / 调工具 / 等审批 / 后台在跑 | 「发送」（旁边另有次要「暂停」） | **补充信息**（steer，不打断、不新开一轮） |
| 正在输出正文（`writing`） | 「暂停」 | 中断这一轮；Enter **静默不提交** |
| 没在跑 | 「发送」 | 开新的一轮 |

`↑`/`↓` 翻历史输入（最近 20 条）：输入法合成期让路、多行草稿光标不在首行时让路（`recall()` :76）。

## 2. `send(text)` —— 业务入口（`chat.ts:1608`）

按顺序做六件事：

```ts
                abortCtl = new AbortController()
6. 建本轮上下文 const ctx: TurnCtx = { sid, segs: [], runId: null, sawTerminal:false,

                                      transportError:false, usage:null }
```

两个刻意的选择：

- **不预建空正文段**（v2.11 改）：旧行为一上来就插一个空占位气泡，只要这一轮开口先调工具，
  界面上就会出现"空气泡 + 工具行 + 正文"。现在**按需创建**：第一段是工具行就是工具行、是正文就是正文。
- **`ctx` 是对象而不是局部标量**：`finally` 里还要读它（相位判定、对账、统计全靠它）。

## 3. 提交（跳 3–4）

```ts
// chat.ts:1093 runTurn()
const sub = await submitRun(text, ctx.sid)      // POST /v1/runs {input, session_id} → 202 {run_id}
ctx.runId = sub.run_id; store.run.runId = sub.run_id
writeActiveRun({ sessionId, runId, sentText: text, startedAt: Date.now() })   // hcl.activeRun
await runEvents(sub.run_id, (n,d) => applyEvent(ctx,n,d), signal)             // GET .../events
```

**"提交"与"订阅"分离**是本项目最重要的一条上游契约：`POST /v1/runs` 立刻返回 `run_id`，
run 的执行**不依赖有没有人订流**（实测：无人订阅的 run 24s 后 completed、正文已落库）。
所以客户端可以在任意时刻"掉线—回来"，而任务不会因此消失。

`writeActiveRun` 写在提交成功之后、订阅之前：从这一刻起页面被冻结/刷新/被系统回收，都不该让这一轮
从界面上消失。

## 5. 解析 SSE（跳 8，`api/sse.ts:21`）

为什么不用 `EventSource`：它**只支持 GET**，而流式聊天是 POST。所以手写
`fetch` + `body.getReader()` + `TextDecoder`。四条规则，每一条都对应一次真实故障：

```ts
decoder.decode(value, { stream: true })     // ① 不带 stream:true → 中文在多字节分片边界乱码
const frames = buf.split(/\r?\n\r?\n/); buf = frames.pop() ?? ''   // ② 最后一段可能是半帧 → 留回缓冲区
if (!frame || frame.startsWith(':')) continue                      // ③ 服务端每 30s 发 `: keepalive`
dataLines.push(line.slice(5).replace(/^ /, ''))                    // ④ 只 trimStart，别 trim 整行
                                                                   //    （否则正文里的换行被吃掉）
try { onEvent(eventName, JSON.parse(raw)) } catch { /* 半帧或非 JSON 忽略 */ }
```

`EventSource` 的另一层问题：它不能带自定义头，也不方便与 POST 流共用同一套 `AbortSignal` 语义。

`api/runs.ts:82` 在解析器之上做一次**事件名归一化**（这是真链路 e2e 抓到的真 bug）：

```ts
// /v1/runs 的 SSE 帧【没有 `event:` 行】，事件名在 JSON 载荷的 `event` 字段里；
// 旧通道 chat/stream 是有的（`_sse_frame(payload, event=name)`）。
const real = name === 'message' && typeof inner === 'string' ? inner : name
```

不归一化的话，所有事件名都是默认的 `message` → 全部落进 `default:` 分支被忽略 →
症状是"没有任何逐字输出，只有轮末对账补回来的一段正文"，看起来像流式坏了、其实只是解析错了。

### 段模型（v2.11 起，交错的由来）

一轮**不再压成一个气泡**，而是按时间排成段：`正文段 → 工具行段 → 正文段 → …`。三条规则一条都不能漏：

1. 相邻**正文**仍然合并（不然一轮碎成十几个小块、每块 24px 缝、复制出来一堆空行）；
2. 一条 assistant **同时有正文和 `tool_calls`** ⇒ 正文段在前、工具段在后（模型先说话后调工具）；
3. `role=tool` 结果行按 `tool_call_id` **回填到"当前工具段"**；当前工具段为空时**新开一段**（孤儿结果行 ——
   宁可多一行，也不把"调过这个工具"这件事丢掉）。

实时侧对应的三个动作：`openTextSeg()`（工具行之后的正文**新开一段**，这就是"交错"的关键）、
`sealTextSeg()`（工具一开跑就封口正文段）、`toolsSegFor()`（本批还在跑就续挂，否则另开一批）。

工具行的成对状态存在两处（`store.run.timeline` 与段里的 `seg.tools`），靠 `syncToolsToMsg()`
**按顺序逐字段拷贝**同步 —— 前提是"两边追加顺序完全一致"（见 `文档/04` B2）。

## 7. 三条支路

### 7.1 审批（人在环 / HITL）

```ts
RunStatus.vue answer(choice) → respondApproval(choice)        // chat.ts:1162
  POST /v1/runs/{id}/approval { choice: once|session|always|deny }
  成功 → approval.resolved = choice（卡片显示"已回话：批准一次，等服务端继续…"）
  失败 → approval.error = 人话文案（409 被翻成"这个 run 当前没有待处理的审批"）
```

要点：**这一轮会真的停住等人回话**（与旧通道"当场 fail-closed 拒绝"是本质区别）；
卡片里的选项不是写死的，是服务端 `choices` 给的（缺字段就兜底 `once/deny`）；
`tool.completed` / 正文事件到达时 `dropResolvedApproval()` 收起卡片。

### 7.2 补充信息（steer / 轮中插话）

```ts
canSteer(): 通道==='runs' && phase ∈ {thinking, tool, approval, background} && 拿得到 runId
steer(text): POST /v1/runs/{id}/steer { text }
             成功 → 才把这句话作为**普通用户气泡**推进列表（无标记）
             409 run_not_accepting_steer → 静默降级（这一轮刚好收尾，不留假气泡、不弹提示）
```

服务端语义（实测）：文本被挂到**最近一条工具结果**的末尾，模型下一次迭代就能看到；
本轮若没有工具批次可挂，会随 `run.completed.pending_steer` 回传 —— 按用户口径**忽略**。
⚠️ 它在服务端不是独立消息，所以**刷新/换设备后不会再以"您的消息"出现**（已接受的取舍）。

为什么不用"再 POST 一次 /v1/runs"来模拟：实测那会在同一会话里**并发跑第二条 run**（两条都 running），
历史落库顺序交叉。

### 7.3 中断（stop）

```ts
stop(): runId = store.run.runId ?? readActiveRun()?.runId      // 后台态也能停（本地没有 abortCtl）
        runs 通道 → void stopRun(runId)     // POST /v1/runs/{id}/stop —— 这才是"取消任务"
        stopRequested = true; clearActiveRun(); stopWatching()
        abortCtl?.abort()                   // 只是"不看了"，服务端那一轮由 /stop 取消
```

**断开连接 ≠ 停止**：`abort()` 只断本地流；旧通道时代"断连接"才是唯一的中断方式（服务端还在跑）。

## 9. 轮末对账（跳 12，`reconcileTurn` `chat.ts:1140`）—— "落库的是权威"

```ts
tailMessages(sid, 60)          // GET /api/sessions/{id}/messages?order=latest&limit=60&offset=0
turnSlice(raw, sentText)       // 从尾部找"内容 == 本次发送文本"的 user 消息 → 取它之后的全部消息
normalize(turn)                // 用与历史**同一个** normalize 重建段
  .filter(role === 'assistant')
replaceTurnSegs(ctx, segs)     // 按 key 把流式期拼出来的段整批换掉
blockFromMessages(turn)        // 安全闸门 BLOCKED 原文（事件里拿不到）→ ⛔ 卡片
if (!store.run.timeline.length) store.run.timeline = toolStepsOf(turn)   // 断线时补齐工具步骤
```

**为什么必须做**：`run.completed` 不带 messages，事件流一次性、不可重连；只信 SSE 拼接的话，
断线那一刻的内容就永久丢了。重建后**实时与历史走同一个 `normalize`，形状完全一致**。

切片安全性有个**巧合式不变式**值得记下来：窗口是"从尾部取 60 条"，而本轮的起点正是自己的用户消息
⇒ 只要本轮用户消息落在窗口内，本轮**全部**消息就都在窗口内；落在窗口外则 `turnSlice` 返回空、
对账整体跳过（**安全失败**，不会丢内容）。但 `replaceTurnSegs` 是**整批替换**：一旦将来改成
按 offset 分页取、或上游改了 limit，前半轮会被静默抹掉（见 `文档/04` B4）。

## 10. 失败矩阵

| 现象 | 走的分支 | 界面 |
| --- | --- | --- |
| 服务端这一轮失败（`run.failed` / status=failed） | `sawError` | 🔴 失败 + 段尾红字（真错误，不清） |
| 本地网络断，服务端仍在跑 | `catch(transportError)` → 状态查询 `stillRunning` | 🟡 忙碌中 + `background` 相位；**红字被清掉**；退避轮询 |
| 本地网络断，服务端其实已完成 | 状态查询 `completed` | 🟢 时刻准备着 + 回读对账补出正文（标"已从服务端会话记录同步回来"） |
| 用户点暂停 | `/stop` → `run.cancelled` | 🟠 已中断 + 「· 已中断」，**不产出本轮统计**（半截的计数会误导） |
| 网关在本轮跑完前重启 | `run.interrupted` / status=interrupted | 🟠 已中断（**不算完成**，也不留 record ⇒ 轮询必须停） |
| 事件流静默结束、没有终态事件 | `!sawTerminal` → `stillRunning` | 继续后台轮询到终态 |
| 状态接口也连不上（离线） | `stillRunning` | 留 record，回前台/网络恢复再试（`watchRun` 不在后台空转） |
| 工具被安全闸门拦下 | `blockFromMessages` → `securityBlock` | ⛔ 卡片 + 按通道区分的人话解释（审批超时/被拒 vs 硬规则） |
| 审批没人回话（300s 超时） | 服务端 BLOCKED 文案 | 同上（提示"再发一次并在卡片上点批准一次"） |

## 11. 与调用链并行的两条"外围循环"

1. **状态灯与秒表**：`RunStatus.vue` 每 200ms `tick++` 驱动 `elapsed` 与 `runStatus()`（纯函数派生四态灯）。
   计时用 `performance.now()` 差值，**不用事件里的 `ts`**（时钟/网络抖动会让数字跳）。
2. **滚动锚定**：`ChatWindow.vue` 同时靠 `watch(tail)`（消息条数 + 末条长度）和 `ResizeObserver`
   （盯**内容容器**，含"加载更早"行）贴底 —— DOM 是**分波**进场的，只靠其中一个会停在半路（实测停在 21%~50%）。
