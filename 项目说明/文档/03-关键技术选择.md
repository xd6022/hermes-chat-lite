# 03 · 关键技术选择

> 每条按 **选择 → 为什么 → 代价 → 证据** 写。代价一栏不是凑数的：这些取舍在 `文档/04` 里会
> 变成"已接受取舍"或"隐患"，评审时可以直接对照。

## A. 形态选择

### A1. 纯前端 SPA，没有自己的后端

- **选择**：Vue 3 + TS + Vite + Tailwind，产物是静态文件；所有数据来自 Hermes HTTP 接口。
- **为什么**：数据真值本来就在 Hermes 数据库里。自建一层后端 = 引入第二套真相 + 多一处要维护的鉴权与部署。
  连接层的问题（跨域、鉴权、缓冲）全部可以在**反代**这一层一次性解决。
- **代价**：`API_SERVER_KEY` 必须由反代注入 ⇒ **反代入口必须加口令闸门**，否则任何知道域名的人
  等于拿到一台能在服务器上执行命令的 agent。这是把"后端安全"换成了"部署纪律"。
- **证据**：`README.md` 架构段；`nginx.conf:71-77`；`vite.config.ts:74-90`（dev 环境同一件事）。

### A2. 同源反代，并且**必须剥掉 `Origin`**

- **选择**：浏览器只打同源路径 `/api`、`/v1`；nginx 用 `proxy_set_header Origin ""`。
- **为什么**：Hermes 的 CORS 中间件在 `cors: false` 时对**任何带 Origin 头的请求**直接返回 403 空 body。
  浏览器所有 POST 都自带 `Origin`，`curl` 不带 ⇒ **命令行怎么测都通，真机浏览器一打开就死**。
  注意这不是"开 CORS 就行"的问题 —— 同源反代本身也不够。
- **代价**：等于把 CSRF 防护的责任从上游挪给了 Caddy 的 `basic_auth`；反代配置成了功能正确性的前提。
- **证据**：`api/hermes.ts:50-60`（把 403 翻成人话并直接给出修法）；`nginx.conf:80-85`；`vite.config.ts:82-89`。

### A3. 走 Hermes 原生端点 `/v1/runs`，而不是 OpenAI 兼容的 `/v1/chat/completions`

- **选择**：默认通道 = `POST /v1/runs` + `GET /v1/runs/{id}/events`。
- **为什么**：OpenAI 兼容端点拿不到 `tool.started` / `tool.completed` / `run.completed` 这类一等事件 ——
  那正是"看不见工具在干什么、不知道这轮结束没"的病根。走原生端点之后还顺带拿到两个能力：
  **审批（人在环）** 与 **真正的中断**。
- **代价**：契约更"内部"：事件名在 JSON 载荷里而不在 SSE 帧头、工具字段叫 `tool` 不叫 `tool_name`、
  没有 `tool.failed`（靠 `error: true`）、`run.completed` 不带 messages —— 每一条都要单独归一化。
- **证据**：`api/runs.ts` 文件头四条本质差别 + `runEvents()` 归一化；`api/types.ts` 的 `SseApprovalRequest`；
  仓库 `docs/plans/2026-09-12-runs-transport.md`。

## B. 传输与生命周期

### B1. 手写 SSE 解析器（不用 `EventSource`）

- **选择**：`fetch` + `body.getReader()` + `TextDecoder({stream:true})`，自己切帧。
- **为什么**：① `EventSource` **只支持 GET**，而聊天流是 POST；② 需要与 POST 流共用同一套
  `AbortSignal` 语义；③ 需要自己控制"半帧缓冲 / 注释帧 / data 缩进"这些细节。
- **代价**：四条容易漏的规则全靠人守（多字节分片、半帧、`:` keepalive、`data:` 后只 trimStart）；
  没有 `Last-Event-ID` 续传能力（上游也不支持）。
- **证据**：`api/sse.ts` 文件头 1–4 条规则 + `consumeSse()`。

### B2. 双通道并存：`runs`（默认）+ `stream`（回退），差异集中在一个归约器里

- **选择**：`DEFAULT_TRANSPORT='runs'`，`setSendTransport('stream')` 可整体回退；两条路共用
  `applyEvent` + 同一套渲染与收尾逻辑。
- **为什么**：迁移期需要"能一键退回旧行为"的保险；差异（事件名、思考提示形态、工具字段名、
  失败判定、`run.completed` 带不带 messages）全部在 `applyEvent` 内部抹平，渲染层无感。
- **代价**：双份维护与语义漂移 —— 文案要按通道分（安全闸门的解释）、`retryTurn` 的判据在
  `stream` 下永远成立（`runId` 恒为 null）等（见 `文档/04` B7）。
- **证据**：`chat.ts:772-784`、`applyEvent` 的 `switch` 注释、`lib/security.ts:46-63`（按 transport 分文案）。

### B3. 提交与订阅分离；**连接不等于任务**

- **选择**：`POST /v1/runs` 拿 `run_id` 就落 localStorage，然后才订流；断流不做重连，只查状态 + 回读对账。
- **为什么**：上游 run 是**服务端自己的任务**，无人订阅也照跑完并写库（实测：无人订阅的 run 24s 后
  completed）。而事件流**一次性、不可重放**（消费后再连同一个 run_id → 404）。
  所以"设计 SSE 重连补事件"是死路，正确的恢复手段只有两个：`GET /v1/runs/{id}` 判状态、
  `GET /api/sessions/{id}/messages` 回读对账。
- **代价**：恢复精度依赖"回读能不能切出本轮"（启发式，见 B4）；轮末统计需要两次额外请求（会话累计做差）。
- **证据**：`chat.ts:1180-1196`（架构前提的长注释）、`applyRunStatus()`、`resumeSync()`；
  仓库 `docs/detailed-design.md` §5.12 与 §12 坑 44。

### B4. 轮末对账：**落库的是权威，SSE 只是提示**

- **选择**：`finally` 里必做一次 `reconcileTurn()`，用服务端 transcript **整批替换**本轮流式渲染出来的段；
  同时用它捞安全闸门的 BLOCKED 原文、补齐工具步骤。
- **为什么**：① delta 拼接在"工具前后的多段正文"上不可靠（实测带前导换行杂质、断线会丢字）；
  ② `run.completed` 不带 messages（runs 通道）；③ 事件流断了就没有第二次机会；
  ④ 重建后实时与历史走**同一个** `normalize`，形状完全一致（否则两种渲染路径会慢慢长歪）。
- **代价**：每轮多一次 GET；切片靠"用发送文本匹配本轮起点"这一启发式；
  `replaceTurnSegs` 是整批替换 ⇒ 一旦切片不完整会**静默丢内容**（当前靠"窗口从尾部取"的巧合保证完整）。
- **证据**：`chat.ts:1112-1159`（`turnSlice` / `reconcileTurn` / `replaceTurnSegs`）。

### B5. 恢复只由"回到前台"驱动，**不做后台保活**

- **选择**：监听 `visibilitychange` / `focus` / `pageshow` / `online` 四个信号 → `resumeSync()`；
  还在跑就按 1s→2s→…→30s 退避轮询，页面不可见时不轮询。
- **为什么**：后台定时器会被 throttle、连接会被系统掐，**后台 JS 里做什么都不可靠**；
  用 `setInterval` 保活 = 费电且不可靠。`pageshow` 单独必要（iOS Safari 的 bfcache 恢复时 JS 状态还在、
  连接已死）；`online` 不看可见性（网络恢复本身值得立刻同步一次）。
- **代价**：回前台那一下会有一小段"正在同步…"的中间态；退避到 30s 时用户可能觉得"没反应"。
- **证据**：`lib/page-lifecycle.ts`（`watchForeground` / `backoffDelay`）、`tickWatch()`。

### B6. "页面之外的记忆"只放 localStorage 的四个键

- **选择**：`hcl.activeRun`（本轮提交记录）、`hcl.ctx.<sid>`（水位"上次已知"）、`hcl.theme`、`hcl.avatar`/`hcl.sidebar`。
- **为什么**：`sessionStorage` 扛得住"刷新"但**扛不住"标签页被系统整个回收后重建"**（真机撞到过：
  提交的那一轮，页面上下文被重建后前端完全不知道有 run 在跑）；`localStorage` 能扛住。
  而**每条记录都必须有清除条件**：`activeRun` 一到终态就清、超 6h 自动作废、指向已删会话则清掉 ——
  否则残留记录会让界面显示假状态。
- **代价**：同设备多标签共享这一条记录（语义上对：那一轮确实在跑）；隐私模式下全部静默降级为"仅本页有效"。
- **证据**：`chat.ts:1198-1260`、`lib/context-cache.ts`、`lib/theme.ts`、`lib/appearance.ts`。

## C. 渲染

### C1. 段模型（`text` / `tools` 按时间交错），而不是"一轮一个气泡"

- **选择**：`UiMessage.kind: 'text' | 'tools'`，一轮里按真实时间排成 `正文 → 工具行 → 正文 …`；
  轮级页脚（统计 /「已中断」/ 错误）挂本轮**最后一个段**。
- **为什么**：服务端落库本身就是分条的（`assistant(正文+tool_calls)` → `tool` → `assistant`）。
  压成一个气泡会把"哪段话之后调了什么"永久抹掉 —— 用户轮中插话时两种排法都不对。
- **代价**：长轮次的 DOM 节点明显变多（当初做折叠就是为此，用户明确选了"常驻小字行"）；
  历史与实时两条路径都要小心翼翼地维持同一套分段规则（三条规则，见 `文档/02` §6）。
- **证据**：`chat.ts:41-82`（`UiMessage` 注释）、`normalize()`、`openTextSeg/sealTextSeg/toolsSegFor`；
  仓库 §12 坑 57/58。

### C2. 无 UI 库：Tailwind + 少量手写组件；hljs 按需注册

- **选择**：不引组件库；`highlight.js/lib/core` + 显式注册 ~19 种语言。
- **为什么**：自用工具，界面需求是"手机原生观感、深色模式、极简"，引库反而是负担；
  hljs 全量 import 会把 190+ 语言打进包（实测 1.17MB），按需注册后包体降到约 1/6。
- **代价**：表格横向溢出这类 CSS 细节要自己修（10 列行情表曾把整个消息区撑宽）；样式契约只能靠
  CSS 回归测试守（`style.spec.ts`）。
- **证据**：`lib/markdown.ts:7-9`、`lib/markdown.ts` 的 `table_open/table_close` 重写、
  `style.css` 的宽度契约；仓库 §12 坑 43。

### C3. 流式渲染用 rAF 节流 + 整段重渲染，不做增量 diff

- **选择**：内容变化 → `requestAnimationFrame` 里 `renderMarkdown(整段)` → `v-html`；
  代码块复制按钮在渲染后注入 DOM（`v-html` 出来的节点拿不到 Vue 作用域）。
- **为什么**：实现简单、行为可预期；markdown 未闭合代码块也不会抛错（markdown-it 当普通代码块渲染），
  逐字渲染因此不需要特殊处理。
- **代价**：长回复 + 多段时 CPU 开销随文本长度线性增长；每次重渲染都要重扫 `pre` 节点补按钮。
- **证据**：`components/MessageItem.vue` 的 `schedule()` / `decorate()`。

## D. 状态与结构

### D1. 不引 `vue-router`：手写 ~70 行 hash 路由，**地址即状态**

- **选择**：`#/s/<id>` = 该会话；裸域名 = 欢迎页；`pushState/replaceState` 后**手动分发**给订阅者。
- **为什么**：收益来自"状态在地址里"（刷新、书签、多标签、返回键、分享链接），**不来自路由库**；
  只有一个参数，手写纯函数还能直接单测，也少一层要跟着升级的依赖。
- **代价**：三条坑自己扛 —— ① `pushState/replaceState` **不触发任何事件** ⇒ 自己的导航必须手动分发；
  ② 欢迎页要把 `#` 整个去掉（`pathname + search`）；③ 同一次变化可能被 `popstate` 与 `hashchange`
  各来一发 ⇒ 要用"最后分发过的路由"去重。
- **证据**：`lib/route.ts` 全部；`App.vue` 的 `applyRoute()`（打开会话的**唯一入口**）。

### D2. 不引 `Pinia`：`reactive()` 单例 store

- **选择**：`export const store = reactive({...})` + 模块级动作函数。
- **为什么**：只有一个会话视图，`reactive` 足够；少一层依赖与心智负担。
- **代价**：**模块级单例 + 模块级可变变量**（`loadedIds`、`abortCtl`、`transport`、`stopRequested`、
  `watching`、`watchAttempt`、`bootErrorTransient`）⇒ 测试必须手工清状态，否则 RED 阶段会**假通过**
  （实测踩过）。
- **证据**：`chat.ts:176` 起、`chat.ts:247-255`、`chat.ts:1274-1277`；
  仓库 §12 坑 64（单例污染测试）。

### D3. 状态灯是**派生量**，不是状态机

- **选择**：`lib/turnStatus.ts` 的纯函数 `runStatus({phase, seconds, runId})` → `{light, icon, text, pulse, retry}`；
  不缓存、不落盘、没有 `start/end` 生命周期。
- **为什么**：判据（尤其"什么时候才红"）是风险最集中的地方，抽成纯函数就能一条一条单测锁住；
  状态机本身是负债（用户明确定过这条）。
- **代价**：每次渲染现算（成本可忽略）；相位语义分散在多处写入点 ⇒ 多一个终态就要改多处，
  所以额外加了**编译期绊线**：`const exhaustive: never = phase`，给 `RunPhase` 加成员会直接编译报错，
  逼着人决定"这个新状态亮什么灯"。（现实教训：上游新增终态 `interrupted` 时四个判据点同时漏，
  界面永久卡在"忙碌中"。）
- **证据**：`lib/turnStatus.ts:116-124`；仓库 §12 坑 68。

### D4. 同一件事只有一个入口（结构性纪律，不是某个 API）

- **选择**："打开哪个会话"只走 `App.vue.applyRoute()`（侧栏点击只是**改地址**）；
  "忙不忙/结束没"只由 `runStatus()` 说；"工具在干什么"只在对话流的工具行里说（状态行不重复工具名）。
- **为什么**：同类信息两处实现 = 下次 bug 的地址（`Sidebar.pick()` 曾直接 `openSession()`，
  与 `resumeSync()` 打架 ⇒ "地址是 B、画面是 A"）；同一件事两处显示 = 用户不知道看哪个
  （轮首灯与状态行 100% 重叠，被撤掉）。
- **代价**：约束是隐式的，靠注释与文档传递；新加入者容易顺手破坏。
- **证据**：`components/Sidebar.vue:56-80`、`App.vue:93-117`；仓库 §12 坑 62/70。

## E. 可信度与边界

### E1. 绝不编数字：只显示有真实来源的量

- **选择**：状态行是 `模型 │ 窗口上限 │ 本轮输入合计`，**没有百分比、没有进度条**。
- **为什么**：Hermes 的 HTTP 层**不提供"当前上下文占用"**（那是 TUI 内部管道）。前端能拿到的
  `usage.input_tokens` 是 `agent.session_prompt_tokens` —— **该轮内每次 API 调用的 prompt 累加**。
  拿它除窗口会得到荒唐的假水位：一轮 30 次调用累出 2.6m ÷ 1m ⇒ 显示 100% 并转红，
  而那一轮**单次最大 prompt 只有 125k（≈12.5%）**。所以只报"本轮输入合计"这个有真实来源的量，
  三段数据缺哪段就少显示哪段。
- **代价**：界面看起来"少了一个大家都有水位条"；上下文快满时用户得不到预警（上游没这个能力）。
- **证据**：`components/ContextGauge.vue` 文件头（含实测数字）、`chat.ts:1847-1864`；仓库 §12 坑 47/52。

### E2. 客户端兜住上游缺陷，但**不碰上游代码**

- **选择**：删除会话后 2s 复查、还冒出来就再删一次（上游异步写 token 计数时会 upsert 重建会话行）；
  安全闸门/审批的文案由前端翻成人话；上游没有搜索接口就在客户端过滤（且必须取满 limit=200）。
- **为什么**：`/opt/hermes` 属 root，改动会被升级覆盖、也不在授权范围内；上游缺陷短期不会修。
  但要划清边界：**能兜的兜（幂等重试、文案、补数据），不能兜的如实说**（不假装成功）。
- **代价**：客户端多了一些"解释上游"的代码；兜底逻辑本身要防重复删（幂等）。
- **证据**：`chat.ts:717-762`（含事故注释与复现脚本路径）、`lib/messages.ts`、
  `lib/security.ts`、`api/hermes.ts:8-11`。

### E3. 构建与部署必须"可核验"

- **选择**：构建期自检产物（缺文件就在构建炸）；`__BUILD_ID__` 构建时注入；
  入口 `index.html` 一律 `no-store` 而带 hash 的资源一年 `immutable`；静态资源缺文件**真 404**；
  healthcheck 打**需要鉴权**的 `/api/sessions` 而不是 `/health`。
- **为什么**：这些都对应过一次"静默的错"：Dockerfile 漏 `COPY public/` 而 SPA 回落把缺文件变成
  `200 + 入口 HTML` ⇒ "图标没生效"被误判成浏览器缓存；`/health` 不带 key 也 200 ⇒ 密钥填错照样 healthy；
  入口 HTML 没 `Cache-Control` ⇒ 手机"刷了好几次还是老版本"。
  **把静默的错变成响亮的错**是本项目的部署哲学。
- **代价**：nginx 配置变长且需要理解优先级（正则 location 锚在根层、`= /index.html` 精确匹配优先）；
  改 `public/` 要同步改 Dockerfile 的自检清单。
- **证据**：`Dockerfile:11-31`、`nginx.conf:25-67`、`docker-compose.yml:16-24`、`README.md` 排错对照表。

## F. 验证策略

### F1. 三层验证阶梯，各管一段，不混用

| 层 | 管什么 | 现状 |
| --- | --- | --- |
| 纯函数 / 组件单测（`vitest`，jsdom） | 判据、分段规则、分页去重、SSE 切片、审批状态机、路由 | 28 文件 / **314 用例**，秒级，全绿 |
| 真链路 e2e（`npm run e2e`，打真 API + 真模型） | 只有它能发现的契约问题（SSE 帧形态、终态语义） | 3 个 spec；抓到过 2 个真 bug（事件名归一化、`run.cancelled` 被判成完成） |
| 真浏览器探针（技能库脚本，真内核 + 本地 dist + 自建反代） | jsdom 抓不到的东西：布局、滚动锚定、地址即状态六条、线上版本指纹 | 已验证多轮；含 A/B 归因以区分"是否本次引入的回归" |

- **为什么**：jsdom **不做布局**（`scrollWidth` 恒 0）⇒ 滚动/宽度类 bug 只能真浏览器抓；
  而真链路 e2e 一轮几十秒还烧 token ⇒ 不能进 `npm test`（`e2e/vitest.config.ts` 与主配置分离）。
- **代价**：三层各有一套环境与坑（探针自身会假绿、假失败）；**没有 CI**，全靠人工按流程跑
  （见 `文档/04` C4）。
- **证据**：`package.json` scripts、`e2e/vitest.config.ts`、`vite.config.ts` 的 `test` 段；
  仓库 §10.1–10.4 的验证证据、§12 坑 41/49/51/55。
