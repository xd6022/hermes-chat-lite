# 04 · 设计缺陷与风险

## 0. 评审口径（先读这段，免得把取舍当 bug）

1. **分级含义**

| 级 | 含义 | 处理方式 |
| --- | --- | --- |
| **A** | **确认缺陷**：能由代码直接推出错误行为（含静默丢数据、状态串台） | 建议修 |
| **B** | **结构隐患**：现在能工作，但依赖隐式不变式 / 上游细节，改动或环境一变就碎 | 排期观察，改相关代码时顺手加固 |
| **C** | **已接受的取舍**：用户明确拍板或上游能力所限 | **不要当 bug 提**，除非有新信息 |
| **D** | **改进建议**：收益明确、成本可估 | 按优先级排 |

2. **本文 A/B 级结论均为静态代码推演**（逐行读 + 交叉验证调用点），**未做运行时复现**。
   标了"置信度"的地方是自评，不是实测。要升级为实测证据，需要按 `文档/06` 的真浏览器/真链路阶梯跑一遍。
3. **服务端没给的能力不算客户端缺陷**。这类一律归到 C，并在条目里写清"上游为什么给不了"。

## A 级：确认缺陷

### A1. 跨会话的 run 状态串台 —— 最严重的一条：在 B 会话里发的话会被注进 A 会话那一轮

> **处理状态**：已记录、挂起（2026-09-18 用户拍板"晚点再处理"）。当前只有静态推演，**未做运行时复现**；
> 复现脚本与修复排期见本文 D 级第 1 条。

- **触发路径**（4 步，全部有代码出处）：
  1. 在会话 **A** 发一轮长任务，事件流丢失（手机切后台/网络抖动）→ `send()` 的 `finally` 判定
     `stillRunning` → `phase='background'`，`store.run.runId` 保留为 A 的 run_id，并起
     **退避轮询** `watchRun(rec)`（`chat.ts:1754-1764`）。
  2. 此时 `store.streaming=false`，**切会话的守卫失效** → 点侧栏进会话 **B** →
     `openSession()` 只重置了 `phase`/`timeline`/分页与上下文，**没有重置 `run.runId` /
     `startedAt`，也没有 `stopWatching()`**（`chat.ts:562-616`）。
  3. 之前那个 `watchTimer` 照样到点触发 → `tickWatch()` → `applyRunStatus(rec)`。
     `rec.sessionId === A ≠ store.currentId === B`，但函数**只检查 run 是否终态、不检查会话**
     → 把 B 的界面改成 `phase='background'`、`store.run.runId = A 的 run_id`（`chat.ts:1324-1351`）。
  4. 于是 B 里：状态行显示 🟡「忙碌中」（还带着 A 的计时）；`canSteer()` 因为
     `phase==='background'` 且 `runId` 非空而**返回 true** → 输入框按钮是「发送」＝**补充**
     → 你打的字被 `POST /v1/runs/{A}/steer` **注进 A 那一轮**，同时作为一条用户气泡**出现在 B 的列表里**
     （`chat.ts:1503-1537`）。
- **附带影响**：此时 B 里的「暂停」按钮指向的也是 A 的那一轮（`stop()` 走 `store.run.runId`）——
  会取消另一个会话的任务。
- **置信度**：高（纯状态读写，路径完整）。**触发需要"phase=background 且切到了别的会话"**，
  在手机上切后台是常态，因此不是罕见路径。
- **修法建议**（成本很小）：
  - `applyRunStatus()` / `recoverTurn()` 首行统一加会话守卫：`rec.sessionId !== store.currentId → stopWatching(); return true`；
  - `openSession()` 里补 `stopWatching()`，并把 `store.run.runId`、`startedAt` 一起归零（与 `goHome()` 的清理保持一致）；
  - `steer()` 再确认一次 `ctx.sessionId` 或至少校验 `store.currentId === rec.sessionId`。

### A2. 跨标签页无互斥：同一会话可以并发跑两条 run

> **处理状态**：已记录、挂起（2026-09-18）。静态推演，**未做运行时复现**；修复见本文 D 级第 2 条。

- **机制**：`send()` 的守卫只看**内存里**的 `store.run.phase`（`chat.ts:1611`），
  而"我提交过哪一轮"的权威记录 `hcl.activeRun` 只在 `resumeSync()` / `stop()` / `canSteer()` 里读。
  已经打开同一会话、且 `phase='idle'` 的第二个标签页（它不会收到任何 `visibilitychange`，
  因为一直处于前台）可以**直接再提交一条 run**。
- **附带影响**：`writeActiveRun()` 是**无条件覆盖**，B 标签提交后会把 A 标签的那条记录挤掉 ——
  A 标签的恢复锚点（runId / sentText）随之丢失，A 的轮末对账会切不中本轮。
- **置信度**：高（静态）；概率取决于用户是否多标签操作同一会话（用户已声明"多标签不实时同步"可接受，
  但**这里不是同步问题，是重复执行问题**）。
- **修法建议**：`send()` 提交前 `readActiveRun()`；若存在且未过期、且指向同一会话 →
  先 `GET /v1/runs/{id}` 判状态，仍在跑就**拒绝并提示**（"该会话在别处还有一轮在跑"），
  或退化为 steer；`writeActiveRun` 改为"仅在无有效记录时写"。

### A3. `steer` 的静默丢弃：输入框已被清空，话却没了

- **机制**：`InputBox.submit()` 先 `text.value = ''`（清空输入框），再调 `steer(v)`；
  而 `steer()` 内部有两处**静默 return**：`if (!content || !canSteer()) return` 与 `if (!runId) return`
  （`chat.ts:1524-1528`）。`canSteer()` 在渲染期算过一次（决定按钮语义），**提交那一刻会重算** ——
  如果这一刻相位刚好落到 `writing`/`done`（典型：这一轮刚收尾），条件不再成立 ⇒ **直接返回**：
  没气泡、没提示、输入框已空 ⇒ **用户输入静默丢失**。
- **对比**：409（run 刚好收尾）那条路径是**故意**静默降级的（用户已定口径）；
  但"文本没进任何地方、界面也没有任何反馈"与那条不同 —— 那是**用户没被告知自己白打了字**。
- **置信度**：高（代码路径明确）；概率中低（窗口小，但恰好是"看着快跑完了再补一句"的常见时刻）。
- **修法建议**：`steer()` 返回 `boolean`，`submit()` 在 false 时**把文本写回输入框**并给一句
  「这一轮刚要收尾，补充没送出去，请直接发送作为新的一轮」。

### A4. Markdown 里的链接点击即整页跳走（SPA 未拦截）

- **机制**：`renderMarkdown()` 产出的 `<a href>` 经 `v-html` 注入，**全仓没有任何 click 拦截**
  （`components/MessageItem.vue` 只给代码块加了复制按钮）。点了链接 = 同标签页导航到外站 ⇒
  SPA 卸载、内存里的会话与滚动位置全丢；回来要靠浏览器返回键触发整页重载
  （在跑的轮次能靠 `hcl.activeRun` 救回，但视图与滚动位置回不去）。
- **附带**：`linkify: true` 会把裸 URL 也变成可点链接，误触概率不低（手机上尤其）。
- **置信度**：高（静态）。
- **修法建议**：渲染后（或在 markdown-it 的 `link_open` 规则里）统一加
  `target="_blank" rel="noopener noreferrer"`；或在 `MessageItem` 上用事件委托拦截 `a[href^="http"]`
  的点击走 `window.open`。

## B 级：结构隐患

### B1. `stores/chat.ts` 一个文件承担 6 类职责 + 7 处模块级可变状态

- **现状**：1899 行，混合了 —— ① 会话/分页 REST 动作；② 段归约（`normalize`/`prependEarlier`）；
  ③ 发送状态机（`send`/`applyEvent`/`finally` 收尾）；④ 断线恢复协调（`activeRun`/`resumeSync`/
  `applyRunStatus`/`watchRun`）；⑤ 统计口径（`counters`/`buildStats`/`rememberContextUse`）；
  ⑥ 上游缺陷兜底（`sweepGhost`）。模块级可变状态：`abortCtl`、`loadedIds`、`transport`、
  `stopRequested`、`watching`、`watchAttempt`、`bootErrorTransient`。
- **为什么是隐患**：A1 这条缺陷本质上是"模块级 run 状态跨越了会话边界"——**单例状态越多，
  跨边界泄漏越难靠 review 发现**；测试也受影响（单例污染会让 RED 阶段假通过，已实测踩过）。
- **建议拆分边界**（按职责，不按行数）：`sessionStore`（列表/分页/CRUD）·
  `turnStore`（相位/计时/timeline/审批）· `transcript.ts`（`normalize`/`prependEarlier`/`toolStepsOf`，
  纯函数可直接搬）· `resume.ts`（activeRun + 轮询 + 对齐）。**先搬纯函数与恢复协调这两块，收益最大、风险最低。**

### B2. 同一份工具状态有两份副本，靠"追加顺序完全一致"这一隐式不变式同步

- **现状**：`store.run.timeline`（状态行/历史统计用）与每个工具段里的 `seg.tools`（对话流渲染用）
  是两份数据；`syncToolsToMsg()` 按顺序**逐字段拷贝**（`chat.ts:928-941`）。
- **风险**：① 上游一旦乱序或补发事件，两边就错位；② `markToolDone(name, status)` **按工具名**
  从尾部找"最近一个 `status==='run'`"的步骤（`chat.ts:1566-1575`）——`/v1/runs` 的
  `tool.completed` 载荷**只有工具名**，没有 call id，所以**同名工具并发**（并行工具调用）时，
  先完成的那条会配到后启动的那步上 ⇒ 耗时/成败错配。
- **建议**：能拿到 id 就用 id；拿不到就退化成"FIFO 配对"（用起始序号而不是"最后一个 run"）；
  长期看把两份状态合成一份（timeline 直接就是各个段的扁平视图）。

### B3. 与上游的契约散落在多处，终态扩展要"人肉 grep"

- **现状**：上游的新终态 `interrupted` 曾经**四个判据点同时漏**（`isTerminalStatus`、`send()` 收尾分支、
  统计判据、`turnStatus`），表现是**界面永久卡在"忙碌中"** + 退避轮询永不停止。
  现在只在 `turnStatus` 一侧加了编译期绊线（`const exhaustive: never = phase`），
  其余判据仍是字符串比较散落在 `chat.ts`。
- **另一面**：契约还耦合到上游**源码行号与文案**（`api_server.py:6604-6622`、
  `"The gateway restarted before this run settled."`、`BLOCKED: approval required (…)` 等）。
- **建议**：把"终态集合/事件名/字段名/关键文案"收成**单一常量模块 + 一个 contract.spec.ts**，
  所有比较点引用它；升级上游时只改这一个文件（顺带就有了"上游改了契约会红"的哨兵）。

### B4. 轮末对账的切片安全靠"巧合式不变式"，而替换是整批的

- **现状**：`reconcileTurn()` 取"尾部 60 条"，再用**发送文本相等**找到本轮起点（`turnSlice`），
  然后 `replaceTurnSegs()` 把流式期拼出来的段**整批换掉**。
- **为什么现在是对的**：窗口从尾部取、本轮的起点是自己的用户消息 ⇒ 只要用户消息在窗口内，
  本轮**全部**消息就都在窗口内；不在窗口内则返回空 ⇒ 对账整体跳过（安全失败，不丢内容）。
- **隐患**：这个正确性依赖"窗口对齐尾部 + 起点=文本匹配"两个前提同时成立。改成按 `offset` 分页取、
  或上游调整 `limit`、或将来给消息补了规范化处理（输入被 trim/加前缀）⇒ **前半轮会被静默抹掉**。
- **建议**：① 加一条断言/注释把这个不变式显式化（`turn.length && turn[0].role === 'user'` 才允许替换）；
  ② `replaceTurnSegs` 前先比对"新段是否覆盖了旧段的全部来源 id"，不覆盖就**只追加不替换**；
  ③ 更彻底：请上游在消息上带 `run_id`，用 id 切本轮（见 D3）。

### B5. 审批卡片只活在事件流里：流一断，卡片消失，run 只能等超时

- **现状**：`store.run.approval` 是 SSE `approval.request` 的**投影**，且 `send()` 的 `finally`
  里会被**清成 null**（`chat.ts:1678`）。若这一轮停在 `waiting_for_approval` 时事件流断了
  （手机切后台的典型场景），恢复路径 `applyRunStatus()` **没有任何重建卡片的途径**
  （`RunStatusResponse` 类型里也没有 pending approval 字段）⇒ 界面显示 🟡「忙碌中」，
  用户既看不到"在等我批准"，也没有按钮可点，直到服务端默认 **300s 超时**后以 BLOCKED 收场。
- **置信度**：中高（本地逻辑确定；"上游 `GET /v1/runs/{id}` 是否含待审批信息"未实测，需真链路确认）。
- **建议**：① 恢复时若 `status === 'waiting_for_approval'`，至少显示一句
  「服务端在等人工审批，但审批详情只走事件流、已丢失」；② 更好的做法是请上游在状态查询里返回
  pending approval（或允许**重新订流**拿到当前待办）；③ 或把"上次相位"落进 `activeRun` 记录，
  回来时据此提示用户"这轮可能停在审批上，建议重发"。

### B6. 每轮统计 = 会话累计做差：并发/多设备/中途刷新会串

- **现状**：`before = counters(sid)`（发送前）→ `after = counters(sid)`（轮末），差值即本轮用量。
  上游**不落库逐轮 usage**（实测：一个真实会话 300 条消息，`token_count` 全空）。
- **风险**：同一会话若有第二条 run（见 A2）或另一台设备在写，做差结果会把别人的用量算进本轮；
  刷新后逐轮统计永久丢失（只有会话累计能长期显示）。
- **上游原因**：要逐轮历史就必须让服务端把 usage 落库 —— 那要动 Hermes 核心，按"不改上游"原则不做。
- **建议**：优先修 A2（消除并发来源）；`buildStats` 增加"异常保护"——差值出现负数或明显异常时
  只显示耗时与缓存率、不显示 token（宁缺勿错）。

### B7. 双通道并存带来的语义漂移

- **现状**：`stream` 回退通道与 `runs` 通道共用归约器，但差异不止事件名：
  安全闸门文案按通道分（`lib/security.ts:46-63`）、审批能力只在 runs 上、`run.completed` 带不带 messages 不同；
  且 `retryTurn()` 的判据是 `store.run.runId !== null` —— **在 `stream` 通道下 `runId` 恒为 null**，
  于是"重试"按钮在"服务端其实已收到（可能已落库）"时也会出现（`chat.ts:1597-1606`，`lib/turnStatus.ts:105-108`）。
- **建议**：要么把回退通道的语义差距在 UI 上标注清楚（已有 `steerUnsupported` 一处），
  要么直接删掉回退通道（它已完成迁移使命），把 `RunPhase`/统计/重试判据统一到单一语义。

### B8. 网络错误判定依赖浏览器英文文案正则

- **现状**：`isNetworkError()` 用固定英文措辞匹配：`Failed to fetch`（Chrome/Edge）、`Load failed`（Safari）、
  `NetworkError when attempting to fetch resource.`（Firefox）、`fetch failed`（undici）。
  刻意**不**用 `e.name === 'TypeError'` 泛匹配（那是为了不把代码里的 TypeError 误报成网络问题，理由充分）。
- **风险**：新浏览器/新引擎/被包装过的错误消息一旦措辞不同，这条判据就失配 ⇒ 文案退化成原始英文，
  且"过时的网络类横幅自动清除"的逻辑（依赖 `bootErrorTransient`）行为随之变化。
- **建议**：判据不变（务实），但把"失配时的兜底"变软：网络层错误统一由 `fetch` 包装函数打标
  （例如 `api/*` 里 catch 后抛一个 `NetworkError` 类型），而不是靠文案识别。

### B9. 单元测试能证明"逻辑自洽"，证明不了"事件源接上了"

- **现状（已发生过）**：滚动锚定的第一版修复单测全绿，真浏览器无效 ——
  因为测试里手动调用了 `ResizeObserver` 回调，而应用代码**根本没 observe 对元素**。
  补救办法（给假 RO 记录 observe 到的元素并断言）只用在这一处，**未制度化**。
- **建议**：凡"事件驱动的修复"，把"事件源确实接上了"作为**必须的一条断言**写进 spec 模板
  （同理适用于 `visibilitychange`/`popstate`/`scroll`/`storage` 等）。

## C 级：已接受的取舍（评审时别当 bug 提）

| # | 取舍 | 为什么这么定 |
| --- | --- | --- |
| C1 | steer 的那句话在服务端**不是独立消息**（挂在工具结果末尾），刷新/换设备后不再以"您的消息"出现 | 上游只有这一个插话语义；用户明确接受 |
| C2 | 长轮次 DOM 节点明显变多；**没有虚拟列表**（几百条消息全量渲染） | 用户明确选了"常驻小字行、不折叠"；虚拟列表会让滚动锚定与复制行为复杂化 |
| C3 | 两个标签打开同一会话**互不实时同步** | 用户已接受（但注意 A2 是另一回事：那是重复执行） |
| C4 | 历史分页 `offset` 锚定在"最新" ⇒ 发过新消息后窗口整体位移、必须按 `srcId`/`loadedIds` 去重 | 上游 `order` 只有 `oldest|latest`，且不返回总数 |
| C5 | 逐轮 token 明细**刷新即丢**（只有会话累计长期存在） | 上游不落库逐轮 usage；要改就得动 Hermes 核心 |
| C6 | 删除是**硬删除不可恢复**，且只提供单行删除、没有任何批量入口 | 有过真实事故（按 source 批量删误删真实会话，页级抢救无效） |
| C7 | 上下文水位**不显示百分比/进度条** | 上游 HTTP 层没有"当前上下文占用"，只有"本轮输入合计"（拿它除窗口会得到 2.6m÷1m 的假 100%） |
| C8 | 不做模型切换 / Prompt 编辑 / 附件 / 语音；Settings 只有连接、外观、头像、快捷键 | 明确冻结范围，防蔓延 |
| C9 | 不做 SSE 重连、不做后台保活 | 上游事件流一次性不可重放；后台定时器不可靠 |
| C10 | 移动端"生成中不许切会话"（点了没反应，地址被撤回） | 与地址即状态配套的守卫，避免"地址 B、画面 A" |

## D 级：改进建议（按性价比排序）
