# 01 · 整体架构

## 1. 一句话架构

**这是一个"没有后端的前端"**：浏览器里的 SPA 直连 Hermes 的 HTTP 接口，鉴权、跨域、缓存这三件
本该由后端处理的事，全部交给**反代层（nginx / vite dev proxy）**和**部署形态（Caddy + basic_auth）**解决。

```
┌──────────┐   https    ┌──────────────────────┐  http(内网)  ┌───────────────────────────┐
│  浏览器   │ ─────────▶ │ Caddy（宿主机）       │ ───────────▶ │ chatlite 容器（nginx）     │
│  SPA 产物 │ ①basic_auth │ chat.1597133.xyz     │             │ 静态产物 + /api /v1 反代   │
└──────────┘            └──────────────────────┘             └──────┬──────────────┬─────┘
                                                                    │②注入 Bearer  │③转 dashboard
                                                                    │  清掉 Origin │
                                                                    ▼              ▼
                                                          hermes:8642         hermes:9119
                                                       （API Server：会话、   （dashboard 后端：
                                                        /v1/runs 事件流）      /api/model/info 窗口上限）
                                                          [net_openclaw 网络]
```

链路要点（每一环都有"漏了就静默坏掉"的性质，逐条都有实测出处）：

| 环节 | 做了什么 | 不做会怎样 |
| --- | --- | --- |
| ① Caddy `basic_auth` | 口令闸门 | **任何知道域名的人 = 拿到一台能在服务器上执行命令的 agent**（Hermes 的工具是真执行的）。⚠️ 401 只代表闸门在工作，不代表上游状态 |
| ① Caddy `flush_interval -1` | SSE 不缓冲 | 流式退化成"等全部返回再显示" |
| ② nginx 注入 `Authorization` | 前端产物里**永远没有 key** | 若把 key 编进产物，F12 可见 |
| ② nginx `proxy_set_header Origin ""` | 剥掉 Origin | Hermes 的 CORS 中间件对**任何带 Origin 的请求**返回 403 空响应 → 命令行怎么测都通、真机浏览器一打开就死 |
| ② nginx `proxy_buffering off / proxy_cache off / gzip off` | SSE 三件套 | 同 ①，流式变一次性返回 |
| ③ 单独转发 `/api/model-info` → `hermes:9119` | 拿上下文窗口上限 | 并进 `/api` 那条会打到 8642 变 404（这个接口**不在** API server 上） |

**架构的关键判断**：它不是"简单版 ChatGPT 前端"，而是一个 **agent 运行时的观测与操控面板**。
所有复杂度都在回答四个问题：

1. 这一轮**现在在干什么**？（段模型 + 工具行 + 四态状态灯）
2. 这一轮**结束了没有**？（显式完成态判定，见 `文档/02` §5）
3. 危险操作**要不要问人**？（审批卡片，人在环）
4. 用户**走开了再回来**，界面怎么追上服务端？（`hcl.activeRun` + 回读对账）

## 2. 分层与依赖

```
components/  ──意图 + 绘制──▶  stores/  ──唯一数据入口──▶  api/  ──fetch──▶  nginx ──▶ Hermes
     │                            │
     └────纯函数调用────▶  lib/  ◀─┘（lib 不认识 store，除了 3 个存储适配器）
```

- **components 不做数据获取**：它们调 store 导出的 action（`send` / `steer` / `stop` / `openSession`…），
  或读 store 的响应式字段。要发请求只能绕过 api 层 —— 而那是明令禁止的。
- **lib 是纯的**：段归约（`normalize` 在 store 里，但它的补充工具 `toolStepsOf` / `argPreview` / `toolFailed`
  在 lib 里）、轮分组（`groupIntoTurns`）、状态灯判据（`runStatus`）、路由解析（`parseRoute`）、滚动锚定
  （`followUntilSettled`）。**判据抽成纯函数是为了能逐条单测**：状态灯"什么时候才变红"风险最集中，
  所以它 100% 是纯函数 + 编译器绊线（给 `RunPhase` 加成员会强制你决定这个新状态亮什么灯）。
- **api 只描述契约**：`types.ts` 是上游返回结构的**白名单快照**（含"实测字段只有这些"的注释），
  `runs.ts` 把两条通道的差异就地抹平（事件名、工具字段名、失败判定）。

## 3. 运行时的四条数据流

### 3.1 冷启动（打开页面）

```
index.html 内联脚本定主题（防深色闪白）
  → main.ts: initTheme() → mount(App)
    → App.onMounted():
        checkHealth()            GET /health           → 顶栏绿点 + 版本号
        loadSessions()           GET /api/sessions?limit=200 → 侧栏（客户端过滤，服务端无搜索接口）
        watchForeground(…)       订阅 4 个"回到前台"信号 → resumeSync()
        currentRoute() + markInitialRoute()
        onRouteChange(applyRoute) + applyRoute(initial)   ← 打开会话的**唯一入口**
        resumeSync()             查"我是否有一轮还在跑"
```

`loadSessions(200)` 取满服务端上限不是为了列表，而是**为了搜索命中面**：Hermes 没有搜索端点，
搜索只能在"已取到的"集合里做，少取一条就等于搜不到那一条。

### 3.2 读历史（切会话 / 翻页）

```
地址变化 → applyRoute() → openSession(id)
   ├─ store.streaming 守卫：生成中不许切会话（返回 {ok:false}，路由层把地址撤回）
   ├─ 清空 → GET /api/sessions/{id}/messages?order=latest&limit=100&offset=0
   ├─ normalize(raw)  → 扁平段列表（text / tools 交错）
   ├─ loadedIds = 本页所有原始 id（去重**必须**用它，不能用界面消息的 srcId）
   ├─ hasMoreHistory = 返回条数 == 一页
   ├─ void counters(id)       GET /api/sessions/{id} → 会话累计 token + 模型名
   ├─ void loadModelInfo()    GET /api/model-info    → 窗口上限（经 nginx 转到 hermes:9119）
   └─ void resumeSync()       对一次账
翻页：loadEarlier() → offset = rawCount（**offset 锚定在"最新"**，发过消息后窗口整体位移 ⇒ 重叠 ⇒ 靠 id 去重）
```

### 3.3 写（发一轮）—— 详版见 `文档/02`

```
InputBox.submit() → send() → runTurn() → POST /v1/runs (202) → GET /v1/runs/{id}/events(SSE)
                                  ↓ 事件归约 applyEvent() 边收边画
                         轮末 finally：查终态 → reconcileTurn() 用服务端 transcript **整批替换**本轮段
                                        → counters 做差算统计 → 落 localStorage 缓存
```

### 3.4 恢复（页面被冻结 / 回收 / 断网后回来）

```
visibilitychange / focus / pageshow / online
  → resumeSync():  读 hcl.activeRun
      ├─ 没有记录 / 当前打开的不是那条会话 → 什么都不做（**v2.12 起不再自动切会话**）
      ├─ 本页还在流式 → 问一次 GET /v1/runs/{id}：已终态就 abort 本地流（让收尾逻辑跑起来）
      └─ 否则 → applyRunStatus()：还在跑 ⇒ 相位转 background + 退避轮询（1s→2s→…→30s 封顶）
                                 已终态 ⇒ recoverTurn() 回读会话补内容、按状态收尾
```

**这一层最重要的架构前提**（也是全项目最反直觉的一点，实测确认）：

> `POST /v1/runs` 只是"提交"。run 由**服务端自己跑完并写进会话**，
> **没有任何客户端订阅也照跑**（实测：无人订阅的 run 24s 后 completed，正文已落库）。

所以"前端连接"与"任务执行"本来就是解耦的 —— 前端要补的只有一件事：**回来时把服务端状态投影成界面状态**。
于是**不需要**引入常驻连接管理器、心跳保活、SSE 重连器（服务端的事件流本来就是一次性、不可重放的），
只需要三件小事：① 提交后把 `{sessionId, runId, sentText, startedAt}` 记进 localStorage；
② 回前台问一次状态；③ 还在跑就退避轮询到终态。**后台 JS 不承担任何保活职责。**

## 4. 状态归属与"真值"哲学

| 层次 | 谁是真值 | 前端角色 |
| --- | --- | --- |
| 会话 / 消息 | **Hermes 数据库** | 投影（`normalize` 成段）；SSE 只是**提示**，落库的 transcript 才是**权威** |
| run 状态 | **服务端**（`/v1/runs/{id}`） | 轮询 + 投影；断流不等于取消，只有 `POST /stop` 才是取消 |
| 打开哪个会话 | **地址栏** | 路由分发 |
| 相位/计时/统计 | 前端内存（不可持久） | 派生量；刷新即失（统计还能靠会话累计重算部分） |

一句可复用的原则：**"事件流是提示，落库是权威，服务端状态是终审"**。项目里三处体现：

- 流式 delta 拼接的内容，轮末会被服务端 transcript **整批替换**（delta 实测带前导换行杂质、断线会丢字）；
- 流丢了但服务端说 completed → 界面必须显示"完成"，并**清掉**传输层留下的假报错（"Failed to fetch"）；
- 连接断了但服务端还在跑 → 相位是 `background`（🟡 忙碌），**绝不是**红/失败（报红会让人以为长任务白费）。

## 5. 刻意不做的事（架构边界）

| 不做 | 原因 |
| --- | --- |
| 不做自己的后端 / 数据库 | 数据真值在 Hermes；自建一层只会引入两套真相 |
| 不改 Hermes 核心（`/opt/hermes` 属 root） | 它只用上游**已有**的 HTTP 端点；上游没给的量就不显示（"绝不编数字"） |
| 不做模型切换 / Prompt / Agent 配置 | Settings 最小化，只做连接状态、外观、头像、快捷键说明 |
| 不做 SSE 重连 / 事件补发 | 服务端事件流一次性、不可重放（消费后再连同 run_id 会 404），设计"重连补事件"是死路 |
| 不做后台保活（`setInterval` 心跳） | 后台定时器会被 throttle，白费电且不可靠；恢复只由"回到前台"驱动 |
| 不做多标签实时同步 | 用户已接受；跨标签的一致性只保证"那一轮真的在跑"这一件事（`hcl.activeRun` 共享） |
| 不做批量删除、不做服务端搜索 | 前者有真实事故（硬删除不可恢复），后者上游没有接口 |
| 不做虚拟列表 | 长会话全量 DOM，用户接受（代价见 `文档/04` C2） |

## 6. 部署形态与"现在线上是哪一版"

```
宿主机 ~/workspace/project/hermes-chat-lite
  ├─ .env   只需要一行 HERMES_API_SERVER_KEY=<64 字符>（从 hermes 部署目录取，chmod 600）
  └─ docker compose up -d --build
        构建期：npm ci → npm run build（含 vue-tsc 类型检查，类型不过不出镜像）→ 产物自检（必须存在 4 个文件）
        运行期：nginx:alpine + /etc/nginx/templates/default.conf.template（envsubst 注入 key）
```

**版本可核验性被当成一等需求**（因为手机缓存曾让人无法判断"线上是哪一版"）：

1. `vite.config.ts` 构建时生成 `__BUILD_ID__`（本机构建是"短 sha · 北京时间"；镜像里没 `.git` 就只有时刻），
   显示位置**只在 Settings → 连接状态**（首屏不摆构建信息）；
2. 入口 `index.html` 一律 `no-store`（否则浏览器按 Last-Modified 启发式缓存 → "刷了好几次还是老版本"），
   带 hash 的 `/assets/` 相反：一年 `immutable`；
3. 判版本用**指纹**而不是"看着像"：入口 bundle 哈希 + 每个版本独有的文案 `grep -c`；
4. 静态资源缺文件必须是**真 404**（`location /` 的 SPA 回落会把缺文件变成 `200 + 入口 HTML`，
   这种静默错曾让"图标没生效"被误判成浏览器缓存问题）。
